Counterexample: insn_mul_ch0 on the tapeout core with a 1-cycle reset (riscv-formal default).
Rows are half-clock samples (row/2 = cycle). Instruction under test: 0x02200533 = mul a0, zero, sp.

What happens:
  - pcpi_wait / pcpi_wait_q in picorv32_pcpi_mul have no reset (pcpi_div gates them with resetn).
  - With a single reset cycle they can leave reset as 1/0 -> mul_start -> a phantom 32-cycle multiply.
  - ~cycle 34: mul_finish/pcpi_ready fire while pcpi_valid=0 and instr_mul=0.
  - ~cycle 35: the core enters ld_rs1 for the real MUL, sees pcpi_int_ready already high and
    retires the stale value 0x949ce5f8 as the MUL result -> rd mismatch (rvfi_insn_check.sv:177).
Silicon impact: none for this SoC - reset_synch.v holds core reset for several cycles (FF_COUNT=5),
which flushes pcpi_wait/pcpi_wait_q. An SoC with a 1-cycle reset pulse would be exposed.
